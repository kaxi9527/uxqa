# UXQA 质量工作流

0.5.0 源码迭代。使用本地内置的规则和知识完成「检查 → 问题处理 → 复检」。没有外部 Skill 目录引用，也没有独立资料浏览器。模型接入中心继续作为可选能力运行。

## 功能分布

| 模块 | 主要动作 | 输出 |
| --- | --- | --- |
| 项目与准备 | 添加项目、确认组件库和规范、设置预览 | 当前项目约束及检查范围 |
| 检查 | 源码扫描、网页检查、可选 AI 设计诊断 | 定位、截图、观察值与覆盖缺口 |
| 问题处理 | UI / UX / 体验筛选、分级、专项修复方案、进度记录、人工观察 | 本轮证据、项目约束与待验证任务 |
| 复检 | 重新检测、对照上轮、核对人工证据 | 仍检出、基线/忽略、未再检出 |
| 项目配置 | 组件库、项目规范、预览设置 | 项目自己的规则优先 |
| 全局设置 | 模型与账号、浏览器组件、MCP | 使用同一个 UXQA 运行环境 |

## 知识如何参与功能

内置的 27 项 UXQA 评审规程涵盖视觉层级、字体、颜色、布局、组件、响应式、素材、图表、任务、表单、状态恢复、文案、无障碍、本地化、引导、动效、性能、手势、平台、原型和交付。

- 自动规则产生事实，再按规则与问题语义选择相关规程，补充分类和验证方法。
- AI 诊断读取适用于截图的规程和当前项目规则；不凭静态截图判断流畅度或完整任务成功。
- 修复说明包含具体问题、影响、修复方向、项目约束和复检步骤。
- 人工观察按实际问题文本关联规程，保留位置、复现过程和处理证据。
- 专项诊断把规程、81 项场景核对要求与 22 类技术栈建议应用到所选轮次，形成可保存的修复方案。这些是知识与待验证要求，不是 81 项已经执行的自动检查。

内置知识是 UXQA 自行撰写的产品规程；本轮曾导入的外部原文、数据集、源码、平台模板及其生成索引已移除。没有复制这些材料后删除其署名的分发方式，也不再宣称完整收录任何外部项目。现有运行时依赖的许可证保持有效。

## 使用专项修复方案

完成一轮检查后，在「问题处理」点击「专项修复方案」。选择诊断重点，可补充本次目标与必须保留的约束，然后「生成并保存」。在窄屏的问题详情中，先返回问题列表。

10 个目标为完整质量诊断、信息层级与布局、设计一致性与组件、任务流程与文案、边界状态与恢复、跨屏与平台体验、动效与连续操作、响应与渲染性能、视觉细节与表达、方案取舍与修复评估。

方案按以下顺序组织：本轮项目约束和覆盖边界、已发现问题及处理决定、针对所选目标的验证任务、当前工程的技术栈注意事项、修复后的复检方法。已接受偏差或人工确认的问题保留原决定；不会自动要求重新修改。已有方案可以重新打开和复制。

方案使用所选检查轮次中的规则和组件快照；项目配置变化后应重新检测。技术栈线索只读当前工程的依赖和清单，不执行项目脚本。技术栈建议不等于对应平台已完成检查。MCP 的 `diagnose_quality` 调用同一诊断能力，输入目标、可选轮次与约束，输出并保存方案。

### 逐项验证与证据

在方案中切换到「逐项验证」，展开一个任务，填写实际操作、设备/页面、观察结果与证据位置，然后保存。四种状态为待验证、记录通过、发现问题、不适用；每次保存都要求证据或理由，包括改回待验证。通过记录来自填写者，不是 UXQA 自动检测结论。不适用与通过分别统计。

可以按状态筛选任务、重新打开记录和查看每次变更的历史。保存失败会保留输入并允许重试。复制方案时附上最新结果和证据；生成时的方案与原始轮次保持不变。新生成的方案从待验证开始，不自动继承旧方案的通过状态。

方案注明依据的检查轮次；与当前查看轮次不同时显示提醒，避免把历史记录当作新一轮验收。

对于「发现问题」的任务，点击「转为问题」会预填已有的人工观察表单，补充位置并确认保存后进入问题处理。验证记录与问题处理状态分别保留，修复后需按原操作重新验证。复检页的「专项验证记录」可以回到这些方案。

旧版只有文字的方案仍可阅读和复制；需要重新生成方案才有结构化任务，不把旧文字解析成虚构的验证结论。MCP `quality_verification` 省略 `plan` 时列出方案；提供 `plan` 时读取任务、进度和历史；提供 `task`、`status`、`note` 时保存证据记录。MCP 写入会单独标明入口，不能凭工具调用成功宣称实际任务通过。

设计、动效、平台与实现知识用于诊断及修复方案。UXQA 不执行候选页面生成、动画实现或源码写回，也不会将生成方案当作验收通过。当前没有与其他工具进行同模型、同任务的对照评测，不能宣称全面等价或超过它们。

## 自动检查与验证边界

| 新增检查 | 观察方法 | 分类与结论 |
| --- | --- | --- |
| 卡片密度 | 多列网格中至少 12 个带标题与操作的同权重条目 | UI 建议；需要查找任务验证，不是审美评分 |
| 操作名称 | 可见按钮/链接缺少可访问名称 | UX 问题；核对读屏与窄屏隐藏文字 |
| 字段标签 | 输入框、选择器、文本区缺少标签/可访问名称 | UX 问题；占位文字不替代标签 |
| 标题结构 | 可见标题层级跨级 | UX 建议；核对内容结构 |
| 过渡属性 | 有时长的 `transition-property: all` | 体验建议；不直接宣称卡顿 |
| 布局动画 | 运行中关键帧修改布局属性 | 体验建议；需性能测量 |
| 减弱动态 | 实际启用减少动态偏好后仍有较长运动动画 | 体验问题；必要动效允许按项目规范确认 |

这些检查接入既有页面扫描、截图、规则等级与关闭理由机制；不只是页面文案。检测覆盖当前访问的页面和状态，隐藏/未触发动画、真实设备流畅度、完整键盘路径和业务任务仍需相应场景验证。

## 问题分类与处理

UI 指视觉呈现；UX 指任务、操作和恢复；体验指反馈、时序、动效与手势。每个问题选择主要影响，其他影响写进描述。严重程度「需要改 / 建议改 / 可以看看」与分类独立。

处理状态为待处理、处理中、待复检、接受偏差、人工确认。后两项要求填写理由或证据，状态不会改写原始检测结果。人工记录是项目级观察，单独标明，不伪装为历史自动结果。

修复后重新检测。消失的问题只标「本轮未再检出」：核对相同规则、路由、窗口和状态后再确认。进入基线/忽略与修复不同，缺少覆盖也不算通过。

处理记录保存在本地数据目录 `projects/<项目ID>/issue-workflow.json`，修复方案保存在 `projects/<项目ID>/diagnoses/<方案ID>.json`，逐项验证历史保存在 `projects/<项目ID>/diagnosis-verification/<方案ID>.json`，均与原始轮次分开。普通检查与专项诊断只读项目代码；明确保存规则、基线、组件同步仍沿用现有写入边界。

## 安装与运行

源码、规程、界面与模型运行模块被编译进 UXQA 自身。运行时不访问其他产品目录。源码检查、分类与记录可本地运行；远端页面、模型调用和首次截图浏览器下载各自需要网络。下载版本以 Releases 实际发布为准；详见 [安装与使用](install-and-use.md)。
